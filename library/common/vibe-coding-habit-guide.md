# 바이브코딩 습관 가이드

## 1. 이 문서의 목적

AI에게 질문해서 좋은 답변을 받는 것과, 그 답변이 내 지식이 되는 것은 다르다.

바이브코딩을 하다 보면 ChatGPT, Codex, Claude, Gemini 같은 AI에게 계속 질문하게 된다. 답변은 많이 쌓이지만, 정리하지 않으면 대부분 채팅 안에만 남는다.

이 문서의 목적은 AI 답변을 단순히 “들은 것”으로 끝내지 않고, 내 프로젝트와 내 판단 기준에 맞게 정리해서 반복해서 쓸 수 있는 지식으로 바꾸는 것이다.

핵심 원칙은 다음과 같다.

```text
AI의 답변은 내 지식이 아니라 재료다.
정리하지 않은 채팅은 기억이 아니라 창고다.
결정은 반드시 한 줄로 남긴다.
모르는 것은 부끄러운 것이 아니라 관리해야 할 부채다.
AI에게 맡길 일과 내가 판단해야 할 일을 구분한다.
병렬 작업은 서로 충돌하지 않을 때만 생산성이 된다.
```

## 2. AI 답변을 바로 믿지 말고, 먼저 분류한다

AI 답변을 받으면 바로 “이해했다”고 생각하지 말고, 먼저 아래 네 가지로 나눈다.

```text
1. 사실
2. 설명
3. 제안
4. 결정 후보
```

### 1) 사실

변하지 않는 정보나 기술적 설명이다.

예:

```text
git status는 현재 작업 폴더의 변경 상태를 보여준다.
git push는 로컬 commit을 원격 저장소로 업로드한다.
```

사실은 `GLOSSARY.md`, `git-github-practice-notes.md`, `learning-notes.md` 같은 문서에 남긴다.

### 2) 설명

개념을 이해하기 쉽게 풀어준 내용이다.

예:

```text
commit은 저장 지점을 만드는 것이고,
push는 그 저장 지점을 GitHub에 올리는 것이다.
```

설명은 내 말로 다시 줄여야 한다. AI의 문장을 그대로 저장하면 읽을 때는 이해되는 것 같지만, 나중에 다시 쓰기 어렵다.

### 3) 제안

AI가 추천한 방향이다.

예:

```text
지금은 기능을 늘리기보다 Git/GitHub 반복 루틴을 먼저 익히는 것이 좋다.
```

제안은 바로 결정하지 않는다. 먼저 내 상황에 맞는지 확인한다.

### 4) 결정 후보

프로젝트나 학습 방식에 영향을 줄 수 있는 선택지다.

예:

```text
Potato’s Day는 Git/GitHub 연습용으로 유지한다.
Living Aegis Origin은 당분간 직접 구현보다 문서 정리 중심으로 진행한다.
Codex 요청문에는 현재 최종 결정과 참고 문서를 명시한다.
```

결정 후보는 반드시 한 줄 결정으로 바꾼다.

## 3. 채팅 후 5분 정리 루틴

긴 대화를 한 뒤에는 바로 다음 형식으로 5분만 정리한다.

```text
오늘 배운 것:
오늘 결정한 것:
아직 모르는 것:
다음 질문:
문서에 남길 것:
내가 이해한 결론 한 줄:
```

중요한 것은 완벽한 정리가 아니라 “채팅에서 빠져나오는 순간”에 최소한의 흔적을 남기는 것이다.

### 예시

```text
오늘 배운 것:
- git status는 현재 변경 상태를 보는 명령어다.
- git diff는 실제 변경 내용을 비교해서 보여준다.
- git push는 commit을 GitHub에 올리는 단계다.

오늘 결정한 것:
- 당분간 Git 연습은 status → diff → add → commit → push 순서로 반복한다.

아직 모르는 것:
- branch를 언제 나눠야 하는지 아직 감이 없다.
- conflict가 발생했을 때 해결 흐름을 모른다.

다음 질문:
- Git branch는 초보자가 언제부터 연습하면 좋은가?

문서에 남길 것:
- git-github-practice-notes.md
- learning-debt-guide.md

내가 이해한 결론 한 줄:
- Git은 파일을 저장하는 도구가 아니라, 작업 흐름을 기록하고 되돌릴 수 있게 해주는 습관 도구다.
```

## 4. 결정은 반드시 한 줄로 남긴다

AI와 대화하다 보면 여러 선택지가 나온다. 이때 가장 위험한 상태는 “대충 방향은 정한 것 같은데 문서에는 없는 상태”다.

결정은 길게 쓰지 않는다. 한 줄이면 충분하다.

좋은 결정 기록 예:

```text
2026-07-04: Git/GitHub 연습은 당분간 commit-gym과 Potato’s Day처럼 작은 프로젝트에서 반복한다.
```

나쁜 결정 기록 예:

```text
Git도 중요하고, GitHub도 계속 써야 하고, 상황에 따라 프로젝트마다 다르게 적용할 필요가 있으며, 나중에 branch도 배워야 한다.
```

두 번째 문장은 생각의 흐름이지 결정이 아니다.

결정 문장은 다음 형식이 좋다.

```text
날짜: 무엇을 / 왜 / 당분간 어떻게 할지
```

예:

```text
2026-07-04: Codex 요청문에는 항상 현재 최종 결정과 참고 문서 위치를 포함한다. 여러 채팅이 같은 맥락을 공유하지 못할 수 있기 때문이다.
```

## 5. 모르는 것은 학습 부채로 관리한다

모르는 것이 많다는 것은 문제가 아니다. 문제는 모르는 것을 계속 채팅 속에 흩어두는 것이다.

모르는 것은 `LEARNING_DEBT.md`에 남긴다.

형식은 단순하게 유지한다.

```text
## Git/GitHub

- branch
  - 상태: 아직 개념만 들어봄
  - 필요한 이유: 여러 작업을 동시에 할 때 필요할 수 있음
  - 다음 행동: 작은 예제로 branch 생성/전환/병합 연습

- conflict
  - 상태: 아직 경험 없음
  - 필요한 이유: 여러 기기나 여러 AI 작업 결과를 합칠 때 발생 가능
  - 다음 행동: 일부러 conflict를 만드는 연습 필요
```

학습 부채는 “언젠가 공부할 것” 목록이 아니다.

다음 세 가지 중 하나로 관리한다.

```text
1. 지금 몰라도 된다
2. 곧 작은 예제로 배운다
3. 프로젝트 진행 전에 반드시 확인한다
```

## 6. 문서 부채도 관리한다

채팅이 많아질수록 문서도 늘어난다. 하지만 문서가 많다고 정리가 잘 된 것은 아니다.

문서 부채는 다음 상태를 말한다.

```text
- 오래된 결정이 아직 최신처럼 남아 있음
- 같은 내용이 여러 문서에 중복됨
- 어디에 무엇이 있는지 모름
- 채팅에는 결정이 있는데 문서에는 없음
- 문서에는 계획이 있는데 실제 작업과 다름
```

문서 부채를 줄이는 기본 원칙은 다음과 같다.

```text
문서는 많이 만들기보다, 다시 찾을 수 있게 만든다.
결정은 DECISION_LOG.md에 모은다.
모르는 것은 LEARNING_DEBT.md에 모은다.
다음 행동은 NEXT_ACTIONS.md에 모은다.
개념은 GLOSSARY.md에 모은다.
```

## 7. AI에게 맡길 일과 내가 판단할 일을 구분한다

AI에게 맡기면 좋은 일:

```text
- 개념을 쉽게 설명하기
- 비교표 만들기
- 문서 초안 만들기
- Codex 요청문 작성하기
- Git commit message 후보 만들기
- 긴 대화 요약하기
- 누락된 항목 찾기
```

내가 직접 판단해야 하는 일:

```text
- 지금 이 프로젝트를 계속할지 줄일지
- 이 제안이 내 수준에 맞는지
- 지금 배울 것인지 나중으로 미룰 것인지
- 어떤 방향이 더 재미있고 오래 갈지
- 최종 결정을 문서에 남길지 말지
```

AI는 좋은 조언을 줄 수 있지만, 내 상황의 우선순위를 완전히 대신 정해줄 수는 없다.

따라서 중요한 질문은 항상 이렇게 바꿔 묻는다.

```text
이 답변에서 내가 지금 당장 결정해야 할 것은 무엇인가?
지금 결정하지 않아도 되는 것은 무엇인가?
문서에 남겨야 할 한 줄은 무엇인가?
```

## 8. 여러 AI와 여러 채팅을 병렬로 쓸 때의 원칙

여러 AI를 쓰는 것은 도움이 된다. 하지만 정리하지 않으면 오히려 혼란이 커진다.

병렬 작업의 기본 원칙은 다음과 같다.

```text
역할이 다르면 병렬로 써도 된다.
결정권이 겹치면 병렬로 쓰지 않는다.
최종 결정은 한 곳에만 남긴다.
```

예:

```text
ChatGPT:
- 전체 흐름 정리
- 학습 습관 정리
- 문서 구조 정리

Codex:
- 실제 repo 수정
- 파일 생성
- 코드 변경
- 테스트 실행

Claude:
- 긴 문서 비판적 검토
- 문장 다듬기
- 다른 관점 제안

Gemini:
- 검색 기반 확인
- 다른 설명 방식 비교
- Google 생태계 관련 확인
```

하지만 다음 상황은 피한다.

```text
- 같은 기능을 Codex와 Claude Code에 동시에 수정 요청
- 같은 문서를 여러 AI에게 따로 고치게 한 뒤 병합 기준 없음
- PM 채팅, Codex 채팅, 일반 채팅에서 서로 다른 결정을 내림
```

병렬 작업을 할 때는 항상 다음 문장을 붙인다.

```text
현재 최종 결정은 아래 내용이다.
이전 대화나 과거 제안보다 아래 결정을 우선한다.
```

## 9. Codex 요청문은 “상황 + 목표 + 금지사항 + 확인방법”으로 쓴다

Codex에게 일을 맡길 때는 단순히 “이거 만들어줘”라고 하지 않는다.

기본 구조는 다음과 같다.

```text
1. 현재 상황
2. 이번 작업 목표
3. 수정할 범위
4. 수정하지 말아야 할 것
5. 완료 후 확인 방법
6. 권장 commit message
```

예:

```text
현재 상황:
- 이 repo는 GitHub Pages에서 실행되는 정적 웹 프로젝트입니다.
- 현재 main 화면은 정상 동작합니다.
- 최근 결정은 README.md와 DECISION_LOG.md를 기준으로 합니다.

이번 작업 목표:
- Git/GitHub 연습용으로 status → diff → add → commit → push 흐름을 안내하는 화면을 추가해주세요.

수정할 범위:
- index.html
- style.css
- script.js
- docs/git-practice-notes.md

수정하지 말아야 할 것:
- 기존 메인 화면의 구조는 변경하지 마세요.
- 새 빌드 도구를 추가하지 마세요.
- package.json이 필요하지 않다면 만들지 마세요.

완료 후 확인 방법:
- 로컬에서 index.html을 열었을 때 새 연습 화면으로 이동할 수 있어야 합니다.
- README.md에 사용 방법이 간단히 추가되어야 합니다.

권장 commit message:
Add Git practice routine screen
```

## 10. 하루 작업을 끝낼 때 남길 최소 기록

작업을 많이 했는데 기록이 없으면 다음 날 다시 헤맨다.

하루가 끝날 때는 최소한 아래 세 줄만 남긴다.

```text
오늘 한 일:
오늘 결정한 것:
다음에 할 일:
```

예:

```text
오늘 한 일:
- Potato’s Day에서 공놀이 화면 비율 문제를 확인했다.
- GitHub Pages deploy 로그를 확인했다.

오늘 결정한 것:
- deploy가 느린 문제는 첫 배포와 서버 상태 영향이 있을 수 있으므로, 반복 실패가 아니면 당장 수정하지 않는다.

다음에 할 일:
- 문서 업데이트 커밋을 먼저 하고, 다음 기능 요청은 그 뒤에 진행한다.
```

## 11. 좋은 바이브코딩 습관은 “많이 묻기”보다 “작게 남기기”다

바이브코딩에서 AI를 잘 쓰는 사람은 질문을 많이 하는 사람이 아니라, 답변을 잘 남기는 사람이다.

좋은 습관은 다음과 같다.

```text
긴 답변을 받으면 한 줄 결론을 만든다.
한 줄 결론을 결정인지, 학습 부채인지, 다음 행동인지 분류한다.
중요한 결정은 문서에 남긴다.
다음 Codex 요청에는 최신 결정을 포함한다.
모르는 것은 부채로 관리하고, 부끄러워하지 않는다.
```

AI는 계속 답변해줄 수 있다. 하지만 내 프로젝트를 오래 끌고 가려면, 결국 내 기준과 내 기록이 필요하다.

## 12. 오늘부터 바로 할 3가지

### 1) 긴 채팅 뒤에는 반드시 한 줄 결론을 남긴다

```text
내가 이해한 결론 한 줄:
```

이 한 줄이 없으면 아직 내 지식이 아니다.

### 2) 결정과 모르는 것을 분리한다

```text
결정:
모르는 것:
```

결정은 `DECISION_LOG.md`에, 모르는 것은 `LEARNING_DEBT.md`에 남긴다.

### 3) Codex에게 요청하기 전에 최신 결정 3줄을 먼저 쓴다

```text
현재 최종 결정:
-
-
-
```

이 3줄이 있으면 Codex가 과거 맥락이나 오래된 제안에 끌려갈 가능성이 줄어든다.
