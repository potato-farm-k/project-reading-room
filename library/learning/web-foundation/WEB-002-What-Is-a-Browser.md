# WEB-002. What Is a Browser

브라우저는 단순히 웹사이트를 “보는 프로그램”이 아닙니다. 사용자의 입력을 받아 URL을 해석하고, 서버에 웹 문서를 요청하고, 응답받은 HTML, CSS, JavaScript와 이미지를 해석해 화면과 상호작용으로 구성하는 실행 환경입니다.

초기의 브라우저는 문서 뷰어에 가까웠지만, 오늘날의 브라우저는 웹 애플리케이션, 게임, 멀티미디어까지 실행하는 플랫폼으로 발전했습니다.

## 1. 학습 목표

- 브라우저가 웹에서 맡는 역할을 설명합니다.
- 주소창에 URL을 입력한 뒤 화면이 만들어지는 기본 흐름을 이해합니다.
- HTML, CSS, JavaScript가 브라우저 안에서 각각 어떤 역할로 연결되는지 구분합니다.
- JavaScript는 언어이고 브라우저는 실행 환경(Runtime)이라는 점을 구분합니다.
- Canvas, WebGL, GPU가 브라우저 기반 그래픽 처리와 어떻게 연결되는지 큰 흐름을 이해합니다.
- 개발자 도구가 웹 문제를 확인하는 관찰 창이라는 점을 이해합니다.
- GitHub Pages 프로젝트가 결국 브라우저 위에서 실행되는 웹 문서라는 점을 연결합니다.

## 2. 왜 브라우저가 필요한가

웹에는 서로 다른 서버에 놓인 수많은 문서와 파일이 있습니다. 사용자가 이 문서를 직접 네트워크 명령으로 요청하고 해석하기는 어렵습니다. 브라우저는 이 과정을 대신 처리합니다.

브라우저는 사용자가 이해하기 쉬운 주소창을 제공하고, URL을 웹 요청으로 바꾸며, 서버가 돌려준 응답을 사람이 읽고 조작할 수 있는 화면으로 만듭니다. 그래서 브라우저를 이해하면 HTML, CSS, JavaScript를 단순한 파일이 아니라 “브라우저가 읽고 실행하는 재료”로 볼 수 있습니다.

브라우저의 역할은 시간이 지나며 넓어졌습니다.

```text
문서 뷰어
  ↓
웹페이지 실행 환경
  ↓
웹 애플리케이션 플랫폼
  ↓
게임 / 멀티미디어 플랫폼
```

이 흐름을 알면 GitHub Pages에 올린 작은 웹페이지도, Canvas 게임도, API를 호출하는 서비스도 모두 브라우저 위에서 실행되는 프로그램으로 볼 수 있습니다.

## 3. 핵심 개념

### 브라우저

웹 문서와 데이터를 요청하고, 해석하고, 실행하고, 화면에 표시하는 Client 프로그램입니다. Chrome, Safari, Firefox, Edge 같은 프로그램이 대표적인 브라우저입니다.

현대 브라우저는 문서를 보여주는 역할을 넘어 JavaScript 실행, 네트워크 요청, 저장소, 그래픽, 오디오, 비디오, 입력 장치 같은 다양한 기능을 제공합니다. 카메라, 마이크, GPU, USB처럼 운영체제에 가까운 기능도 제한된 권한 안에서 웹 애플리케이션에 제공할 수 있습니다.

### 주소창과 URL

주소창은 사용자가 웹 자원의 위치를 입력하는 곳입니다. 브라우저는 주소창에 입력된 URL을 해석해 protocol, host, path, query 같은 정보를 구분합니다.

```text
https://example.com/docs/start.html?mode=read
│       │           │                │
protocol host        path             query
```

### 요청과 응답

브라우저는 URL을 바탕으로 서버에 HTTP 요청을 보냅니다. 서버는 HTML, CSS, JavaScript, 이미지, JSON 같은 파일이나 데이터를 HTTP 응답으로 돌려줍니다.

### HTML, CSS, JavaScript

- HTML은 문서의 구조를 만듭니다.
- CSS는 구조에 모양과 배치를 적용합니다.
- JavaScript는 상태, 동작, 입력 처리와 같은 상호작용을 만듭니다.

이 문서에서는 세 문법을 깊게 다루지 않습니다. HTML, CSS, JavaScript는 이후 문서에서 각각 별도로 학습합니다.

### 렌더링

렌더링은 브라우저가 받은 문서와 스타일을 해석해 실제 화면으로 그리는 과정입니다. 사용자는 파일 자체를 보는 것이 아니라 브라우저가 해석하고 구성한 결과를 봅니다.

### JavaScript 실행 환경

JavaScript는 언어이고, 브라우저는 그 언어를 실행하는 환경(Runtime) 중 하나입니다. 버튼 클릭, 키보드 입력, Canvas 그림 그리기, API 요청 결과 표시 같은 동작은 브라우저가 JavaScript를 실행하기 때문에 가능합니다.

JavaScript는 브라우저에서만 실행되는 언어는 아닙니다. Node.js 같은 서버 환경에서도 JavaScript를 실행할 수 있습니다. 이 문서에서는 브라우저가 제공하는 실행 환경에 집중합니다.

### 그래픽 처리

브라우저는 단순한 문서 표시뿐 아니라 Canvas와 WebGL을 통해 그래픽도 처리할 수 있습니다. 복잡한 2D/3D 그래픽이나 게임 화면은 GPU의 도움을 받아 더 빠르게 그릴 수 있습니다.

```text
JavaScript
  ↓
Canvas
  ↓
WebGL
  ↓
GPU
```

처음부터 이 내부 구조를 깊게 알 필요는 없습니다. 지금은 브라우저가 게임과 멀티미디어를 실행할 수 있는 플랫폼으로 발전했다는 큰 흐름만 잡습니다.

### 개발자 도구

개발자 도구는 브라우저가 무엇을 요청했고, 어떤 파일을 받았고, 어떤 오류가 났는지 확인하는 도구입니다. F12 또는 브라우저 메뉴로 열 수 있으며, HTML, CSS, JavaScript, 네트워크, 성능, 메모리 문제를 분석하는 종합 진단 도구에 가깝습니다.

처음에는 Elements, Console, Network 탭부터 익히면 충분합니다. 이후 성능 최적화가 필요해지면 Performance와 Memory 탭도 함께 보게 됩니다.

## 4. 실제 동작 과정

주소창에 URL을 입력했을 때 단순화한 흐름은 다음과 같습니다.

1. 사용자가 주소창에 URL을 입력한다.
2. 브라우저가 URL을 해석한다.
3. 브라우저가 서버에 HTTP 요청을 보낸다.
4. 서버가 HTML, CSS, JavaScript, 이미지 같은 파일을 응답한다.
5. 브라우저가 HTML을 읽어 문서 구조를 만든다.
6. CSS를 적용해 화면의 모양을 정한다.
7. JavaScript를 실행해 상호작용을 만든다.
8. Canvas나 WebGL을 사용하는 경우 그래픽 처리 흐름을 통해 화면을 그린다.
9. 최종적으로 사용자가 보는 화면이 만들어진다.

```text
사용자
  ↓ URL 입력
Browser
  ↓ HTTP 요청
Server
  ↓ HTML / CSS / JavaScript / 이미지 응답
Browser
  ├─ HTML로 구조 만들기
  ├─ CSS로 모양 적용하기
  ├─ JavaScript 실행하기
  ├─ Canvas / WebGL 그래픽 처리하기
  └─ 화면 표시하기
```

실제 브라우저 내부에는 파싱, 스타일 계산, 레이아웃, 페인팅, 합성 같은 더 세부적인 단계가 있습니다. 지금은 “요청한다 → 해석한다 → 실행한다 → 화면을 만든다”는 큰 흐름을 먼저 잡습니다.

## 5. 자주 하는 오해

- **브라우저가 인터넷인가?** 아닙니다. 인터넷은 네트워크 기반이고, 브라우저는 그 기반 위에서 웹을 사용하는 프로그램입니다.
- **브라우저는 HTML 파일만 보여주는가?** 아닙니다. HTML뿐 아니라 CSS, JavaScript, 이미지, 폰트, JSON 등 여러 자원을 함께 요청하고 처리합니다.
- **GitHub Pages에는 서버가 없는가?** 동적 서버 코드를 직접 운영하지 않을 뿐, 정적 파일을 전달하는 서버나 CDN은 여전히 존재합니다.
- **JavaScript는 브라우저 그 자체인가?** 아닙니다. JavaScript는 언어이고 브라우저는 그 언어를 실행하는 Runtime 중 하나입니다.
- **JavaScript는 서버에서만 실행되는가?** 아닙니다. JavaScript는 브라우저에서도 실행되고, Node.js 같은 서버 환경에서도 실행될 수 있습니다.
- **브라우저로 게임이나 3D 그래픽을 만들 수 없는가?** 아닙니다. Canvas, WebGL과 GPU를 활용하면 브라우저에서도 게임과 그래픽 애플리케이션을 만들 수 있습니다.
- **개발자 도구는 오류 메시지만 보는 곳인가?** 아닙니다. HTML 구조, CSS 적용, JavaScript 로그, 네트워크 요청, 성능과 메모리까지 확인할 수 있는 진단 도구입니다.
- **화면에 보이면 파일 경로가 맞는가?** 일부 파일은 보이더라도 다른 이미지나 스크립트가 404일 수 있습니다. Network 탭으로 실제 요청 URL을 확인해야 합니다.

## 6. 프로젝트 적용 예시

### Potato's Day

Potato's Day를 GitHub Pages에서 열면 브라우저가 HTML, CSS, JavaScript와 sprite 파일을 받아 실행합니다. 작은 웹 게임처럼 보여도, 실제로는 브라우저가 파일을 요청하고 JavaScript를 실행해 화면과 애니메이션을 만드는 흐름입니다. 개발자 도구의 Network와 Console 탭은 sprite 파일 누락이나 JavaScript 오류를 확인하는 출발점이 됩니다.

### Living Aegis Origin

Living Aegis Origin 같은 Canvas 2D 기반 게임도 브라우저가 JavaScript를 실행하고 Canvas에 그림을 그리는 예시입니다. 게임 루프, 입력 처리, 화면 갱신은 모두 브라우저가 제공하는 실행 환경 위에서 동작합니다. 그래픽 요구가 커지면 Canvas, WebGL, GPU의 관계를 이해하는 일이 중요해질 수 있습니다.

### 공공데이터 기반 서비스

공공데이터 기반 서비스에서는 브라우저가 사용자의 입력을 받고, API 요청 결과를 화면에 보여줄 수 있습니다. 이때 요청 URL, 응답 형식, CORS, status code를 이해하면 “왜 데이터가 안 보이는지”를 더 정확히 진단할 수 있습니다. Network 탭은 실제 API 요청과 응답을 확인하는 가장 중요한 관찰 지점입니다.

## 7. 실습 과제

1. 자주 여는 웹 페이지 하나를 열고 주소창의 URL을 protocol, host, path로 나눠 적습니다.
2. 개발자 도구의 Network 탭을 열고 첫 HTML 요청과 CSS, JavaScript, 이미지 요청을 구분합니다.
3. Console 탭에서 오류 메시지가 있는지 확인하고, 오류가 있다면 어떤 파일에서 발생했는지 기록합니다.
4. GitHub Pages 프로젝트 하나를 열고 `index.html`, `.css`, `.js` 파일 요청이 실제로 성공하는지 확인합니다.
5. Elements 탭에서 HTML 구조와 CSS 적용 결과를 함께 확인합니다.
6. 버튼이나 입력창이 있는 페이지에서 상호작용 전후로 화면이 어떻게 바뀌는지 관찰합니다.
7. Canvas를 사용하는 페이지가 있다면 JavaScript가 화면을 직접 그리는 예시로 기록합니다.
